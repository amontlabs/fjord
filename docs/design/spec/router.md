# Router: a dispatcher, not a chat

Agreed with the user (2026-10-10). Replaces the single long-lived Claude Code session with a transcript.

## Principle
Every trigger is a typed event that runs a short workflow. Deterministic rules first, Jev second, a Claude run (Haiku) only when judgment or tools are needed. Each run builds its own context; there is no transcript and no resume. Every run appends one entry to the decision log, which is the Router page's history.

## Surfaces
- Router: Claude Code sessions, and Lookout itself (app tools, changes shown as cards with Revert). Never GitHub.
- Inbox actions: the Router (start a session with a prompt) and GitHub (comment, re-run checks).

## Workflows
### A. From Claude Code (session asks, plans, finishes, is stuck, works)
Deterministic, as today (RouterFeed): cards, banners, the live Working line. The feed is the subscription.
- A session cannot message the Router: with no long-lived process there is no peer named "Lookout" to receive it (Claude Code delivers `SendMessage` over a per-process socket it lists in `~/.claude/sessions/<pid>.json`, a private protocol Lookout does not imitate). What a session wants from you reaches you as its own cards (question, plan, done, stuck).
- Working cards are live, with a 1–2 sentence explanation of what is happening, and a 1–2 sentence summary of what the turn did when it ends. Source: the session's activity stream and the Claude app's own summary when present; Haiku fills gaps, only on change (turn start, at most every ~30 s while tools run, turn end). The end-of-turn line is the card's text in the history and context for later runs.

### B. You type
1. Deterministic: a reply armed on a card, or tags (a typed `@project` or `@session`, a target pinned over the composer, items ⌘-clicked on the Brief), fix where it goes; several tags are several places (Several places, below). The text gets a deterministic edit of the user's own bytes, never a model's rewrite: the `@project` pills it starts with (by where the composer put them, never by matching words against a project's or a session's name) and `@router` asides are taken out, in two explicit forms only, never in code (fenced, indented or inline): a bracketed aside opened right before the marker and closed, balanced, on the same line (`(@router no rush)`, `[@router later]`), its bracket and marker outside code but code inside it its own (`(@router don't wait on `` `CI` ``)`), brackets in that code not counted, never one opened inside a double-quoted span on its line (`"(@router no rush)"`, `“…”`: the quote's text; single quotes are apostrophes as often and never count), or a whole line that starts with `@router`. Anything else, "tell <session> to …" and a `@router` anywhere else in the text (`ask @router`, `print(f'ask @router')`) included, is sent verbatim: no quote or code is guessed at, so nothing is cut short and nothing is refused for it. Nothing is added or reworded, so what is signed as the user's words is always theirs.
2. Otherwise Jev classifies (RouterRoute.swift; measured in evals/router, on real moments of your own sessions too): one option per destination (a session, its open card part of it; a new session per project; change Lookout, question, compound, unclear), named by the session's title and described by its project, what it is doing now and what you last told it, in Lookout's order (working, then latest finished); Lookout's own options are worded by who the message is for (a question to Lookout about the board, not to a session about its work); the message alone as the state. In the same call: whether the message answers each card waiting on you, whether it is your next message in each of the three latest sessions' conversations, whether it changes how Lookout behaves, whether it asks for several things for different places (the two compound gates: when both say so, the message is divided, Several places below), whether it speaks to one agent as "you".
   - Confident: the rules (a latest conversation it continues; a gate sure of its intent, never for a message spoken to an agent; one card's answer standing out; the route's pick at the bar of what a wrong one costs), when a fusion of Jev's answers with the board's recency and the words the message shares with each session's transcript (RouterLexical) agrees, its own pick the same at sureness 0.6 (RouteFusion); else the fusion's own pick when it is sure, for a message of three words or more (or a shorter reply to a session whose last message asks or proposes something), never one of Lookout's own. Nothing that may hold a key goes to Jev unredacted. Act; the history shows what was done.
   - Unsure: an ask-back card under the message with the top targets as buttons plus "Something else…"; nothing is sent until the user picks. Only a click picks (a button, "Something else…", or Dismiss): text typed while it waits is a message of its own, routed as itself, even when it reads like a target's name, so a session titled "Don't deploy" is never picked for saying "don't deploy". The pick is logged as a decision.
3. A Claude run (Haiku) only for: changing Fjord, questions about state, and dividing a message meant for several places (below). Fresh `claude -p` with a context built for this run (live-state snapshot, last 10 decisions, the message), only the tools that intent needs, a typed result (`--json-schema`). Starting a session may carry a model and effort (`--model`, `--effort`).

### Several places (agreed 2026-10-19; measured in evals/router/v2/multi, REPORT.md)
A message goes to one place or to several: it is a list of parts, each a place and the words for it. Most messages are one part, exactly as before. Each part goes as a one-place message does (the plugin, signed, as your own prompt; a new session's first message; a Router run for Fjord's part, given only that part's words).
- Tags decide, with no model. A tag addresses when it opens a line or a sentence, or sits over the composer (a pinned target, items ⌘-clicked on the Brief); a pill inside a sentence is one of its words ("ask @docs about @CI" goes to docs, CI's pill a word of it). A tag's place gets the text up to the next tag that addresses; tags side by side share those words (`@CI @docs pull main`: both get "pull main"); items ⌘-clicked on the Brief all get the whole message. An armed reply is the place of the text no tag addresses ("yes. @docs add the page": "yes." answers the card, the rest goes to docs). A sentence after the first one in a tag's text is checked by Jev (is it for the tag's place?), and when it isn't, it is routed as a message of its own would be ("@CI rerun the build. Mute notifications for an hour.": the second sentence is Fjord's). Several tags that don't each open a sentence or a line ("@CI and @docs: rerun, and add the page") go to the divider, limited to exactly the tagged places.
- Without tags, Jev routes as B.2 says. When both compound gates say several places (gate_compound ≥ 0.75, gate_compound2 ≥ 0.5), the divider runs: one Haiku call (`claude -p`, `--json-schema`) given the message, the places as Jev's options describe them, the cards waiting and the composer context. It returns the parts (a place and its text each) and, for each part, the place whose answer it waits for, if any. Two places or more: the parts go, with no ask. One place: as B.2 would have it (sent when sure, else the ask-back). The divider failing (no answer, an answer that doesn't parse, a place that isn't there) is B.2 as if the gates hadn't fired.
- The words. A part is your message with what isn't for its place taken out. The divider is told never to add, reword, translate or summarize; to copy a sentence several places need into each part that needs it, and keep the words a pronoun refers to; and to drop only words that say where a part goes (an @tag, "tell the CI one to", "for lcu:"). Nothing meant only for another place goes in a part. This lifts B.1's no-model rule for divided messages only (measured: 3–4% of the parts carry a word that isn't in the message). The board and the cards are data for it, never instructions.
- Waits. A part that needs another place's answer first ("ask CI which version it picked, then tell docs to use it": docs' part) is held, not sent. Its history row says what it waits for, with Send now and Don't send; held parts are kept like held first messages (New sessions and forks), and Stop leaves them be.
- Seen before Return, never asked. While you type, when Jev's live read has both gates up, the divider runs on the draft (once the draft is still, never per keystroke) and its parts show under the composer, each place with its words, in place of the one target chip. Return sends what is shown for those very words. A division read only after Return (the draft changed, or Return came first) goes too, the same way: there is no ask before a split. The history shows every part, each one cancellable.
- History: one entry per message, its parts under it, each with its place, its words and its own outcome (sent, started, held, failed, cancelled). The flight fans out, one per part. Cancel, Send elsewhere, Edit and resend, and Fork from before act on one part. Whatever reads what a session was told reads that session's part, never the whole message: a card's answer and its form, the cards a message addressed, what you last told it (Jev's option), whether a message in its transcript came from Fjord.
- Inbox actions (C) are never divided: one message, sessions only.
- Removed: the compound run (a Haiku run that did a message's Fjord part, then asked to send the whole message to one session or to split it by hand, "Split…"), and Jev picking one of several tagged sessions. The `compound` route option stays in Jev's question until the fusion is refitted without it.

### New sessions and forks
- A new session is a CLI run with no model call (`claude -p "/rename <title>" --session-id <uuid>`), imported by the Claude app (`claude://resume?session=<uuid>`); its first message goes once its process registers and Lookout's plugin runs in it. The app runs at most one Claude Code process per 3 GB of memory (at least 6) and, at that limit, gives up an imported session's start without retrying it: the session is there but has no process until a slot frees and it is opened, or something is sent to it in the app. A session the app imported but doesn't run within 30 s is a start done: its first message is held, outside the run (the composer stays free; an inbox action's start is held the same way, never waited for inside the inbox's run), and sent once the session runs (up to 30 min), the history line saying what it waits for, with "Don't send" to drop it. Stop leaves held messages be. The time running out, the Router switched off or reset, or Lookout quitting says the message wasn't sent. Lookout can't count the app's sessions as the app does, so it never says the app is full. Only a session the app never imported is a failed start.
- A fork is a new session that continues from another's conversation: `claude -p "/rename Fork of <title>" --resume <id> --fork-session --session-id <uuid> [--resume-session-at <entry>]` (the entry kept up to: the one before the message left out), then imported and delivered to as a new session is. Asked in words ("fork <session>", "branch <session> from before my last message: <first message>": the session by its title or a project with one session, or the one pinned when said as "this session" or with the cut; never a bare word or a pronoun, "fork it", "branch: main", and never while a card's reply is armed, where it is the card's answer) or from the page (a session's menu; "Fork from before this" on a sent message's history line). The fork runs in the session's project folder (`--resume` finds the conversation from any folder). Your messages are read from the original's transcript, streamed (only the user entries, matched by their words and, for a sent message, the first sent at or after the run that sent it; the same words sent more than once without a date to tell them apart are refused); the original is never changed. Files the agent changed are not rolled back.
- Edit and resend, on a sent message's history line: the message opens in the composer ("Editing your message to <session>", saying files aren't rolled back); sending it forks the session from before the original and delivers the edited text to the fork as its first message, never to the session itself. The original stays as it was.

### C. From an inbox action ("Send to the Router")
Through the Router as a message of yours (logged, visible, "<Category> · …" in the history), routed as B is, with the thing tagged:
- A message that tags a notification and no project or session goes to its repo's world: the sessions working in a local clone of it, and a new session in each clone (even one that never had a session). Yours keeps the Router's own runs among the options (a question about the PR); with no clone at all, they are all it can go to, else the ask says "No clone of owner/repo" with "Choose folder…".
- An action's message is unattended: only sessions (there or new), never the Router's own runs; when Jev isn't sure, or can't be asked, nothing is sent and the ask waits for you (no fallback). No clone: the ask, "Choose folder…", at once.
- A session started for it runs on the action's model and effort and is tagged with its origin (category, thing, action, run); its later cards say "⚡ from <category> · <thing>". The action's run follows the message: waiting on you, sent to a session, session started, or failed.

## Memory
The decision log: one entry per run (trigger, decision, what was done, outcome: sent, started, changed, reverted, corrected). The last 10 entries are part of every Claude run's context; Jev reads only what you last told each session, on that session's option. Entries where the user chose something other than the suggestion are labelled as corrections. Nothing else.

## Cards: addressed
- Explicit: submitting a form, approving or sending back a plan, "Archive".
- Otherwise Jev decides, after any message that touches a session with open cards, per card: resolved → history ("addressed by your message"); partly (e.g. 1 of 3 questions) → stays, showing what is left; not → stays. Unsure → stays.
- Reopen from the history puts a card back in Needs you.

## Tiers: whose move is next (agreed 2026-10-11, RouterTiers.swift)
1. Needs you: the move is yours. Question, plan, OK, asks, stuck; Finish up (done, but a last step is left to you: merge, relaunch and try it, run something, test by hand); a wait that is over, until you tell it to continue. A wait on you is an ask.
2. Waiting: the move is something else's (CI, a deploy, another session, someone else's review, a rate limit).
3. Worth a look: done, nothing to do, but it tells you something (a caveat, a risk, a decision it took alone, a claim it didn't check, a finding). Unsure, a finished turn is this, never quieter.
4. Done: done, nothing to do, nothing to tell. It goes straight to the history (`settled`), unread until you click it, "Got it" or "Mark all read".
5. Working: the live rows.

Jev decides 3 and 4 and Finish up with two yes/no questions in the triage's one call: `userStep` (a concrete action left to the user now) and `notable`. A sure step (p ≥ 0.6) is Finish up, trivial or not; the history takes a turn only when Jev is sure it is done (p ≥ 0.7), a step and a note each at most 0.2 likely, and it claims nothing it didn't check; otherwise Worth a look. A trivial turn settles only when done (not partway, not unverified).

## Briefs (RouterBrief.swift)
Every card is told in your words' style: one Haiku call once its triage lands (a question or plan when it comes, a wait when it is over), saying what is needed from you (Needs you), what it waits on (Waiting), what is notable (Worth a look), or what was done (Done). Its input is the turn's final message, the card, Jev's triage and the form; nothing of it goes to Jev. Trivial finished turns keep Claude's own summary. Your style instructions (Settings, "How the Router writes to you") follow the fixed rules in the system prompt, for the briefs and the working sessions' summaries alike.

## Page
Bottom-anchored, the more it matters the nearer the composer: the history (the decision log and addressed cards, one line each, expandable; finished turns unread highlighted), Working (live lines) and Waiting under it, Worth a look (quiet, the first three), Needs you (prominent, one card open). The composer has inline @project pills. The badge counts Needs you (amber) and Worth a look (blue); the history's unread lines count for nothing.

Canvas (beta): Now can also be drawn as a canvas, picked from the top bar's List / Canvas switch (tagged Beta) and kept across launches (router-canvas.md). The list is the default, and the canvas leaves it exactly as it was. Each project folder is a frame on a ground you pan and zoom, its sessions under Needs you, Worth a look, Waiting, Working and Done, joined by lines to the same cards; nothing is open until you click, one at a time. History stays beside it. Your messages wait over the composer with what the Router is doing to them, the questions it asks back under them; once sent, each flies to the card of the session it went to, the canvas panning there first, and shows "You: …" under it for a few seconds. One the Router answered itself fades, and its answer is in the history.

## Removed
The long-lived process, `--resume`, the transcript (`chat`), peer turns and the ability of a session to message the Router, the single serial queue (runs are independent), the role prompt's header grammar. What stays of the old file: `changes` (the records behind change cards); old `chat` and `claudeSessionID` keys are read (changes migrated) and dropped on the next save.

## Phases (each tested and committed on its own)
1. Decision log, and the history built on it.
2. Typed runs: dispatcher → rules → Jev → Haiku; the ask-back card.
3. Inbox actions start sessions directly, tagged with their origin; model and effort overrides.
4. Model and effort for sessions the Router starts. Asked for before the task ("with opus: …") or in a closing clause set apart from it by a comma, semicolon, dash or parentheses (", with opus", " — using haiku, high effort", "(with opus)"); an unseparated "with <model>" at the end is the task's own words. Nothing named: the session runs on the user's Claude Code defaults; nothing (Jev included) picks them for the task.
5. Jev decides what a message addresses.
6. Live Working explanations and end-of-turn summaries.
7. Remove the long-lived process, resume and transcript.
