## 0. Headline for Fjord
- Everything an external process needs already exists as **one HTTP MCP endpoint `/mcp`** on the local server (OAuth or bearer) and the **`t3 thread` CLI**, which is just a thin MCP client of that endpoint (apps/server/src/cli/thread.ts:205-245).
- There is also a full **WebSocket RPC** (packages/contracts/src/rpc.ts, `WS_METHODS` :408-615 and `ORCHESTRATION_V2_WS_METHODS` orchestrationV2.ts:3574) with `orchestration.subscribeShell` / `subscribeThread` streams: this is the real "watch sessions" feed (live thread shells with status, pendingRuntimeRequest, latestVisibleMessage, linked PRs). Needs a session with `orchestration:read` scope (scopes listed in `t3 pair --help`).
- **No outbound hooks/webhooks to external programs** (section 6). Inbound webhooks exist (scheduled tasks), PR watching exists but wakes *agents*, not external programs.

## 1. Orchestrator MCP server
Docs: docs/orchestration-v2/orchestrator-mcp-server.md. Code: apps/server/src/mcp/. Endpoint `http://127.0.0.1:<port>/mcp` (doc :32-36); server key `t3-code`.

### Who can use it / auth
1. **Agents inside T3 threads**: per-provider-session bearer token from `McpSessionRegistry` (scoped to env+thread+provider instance+session; revoked on release; 24h idle liveness window, mcp/McpSessionRegistry.ts:~50). Injected into Codex/Claude/Cursor/Grok/ACP/Pi (doc :58-185). Capabilities: preview, orchestration, worktree, device, pull-requests (McpInvocationContext.ts:14-20).
2. **External MCP clients (outside agents)**: docs/user/outside-agents.md. OAuth 2.1 + PKCE, dynamic client registration (`/oauth/mcp/register|authorize|approval|decision|token`, environmentHttp.ts:623-645; auth/McpOAuth.ts:88-98). Human approves in a browser page (pairing code from `t3 auth pairing create` or signed-in browser session). Access levels: read-only (default) / supervised … full-access; children cannot exceed approved mode. Session lasts **30 days** (EnvironmentAuth.ts:78). Scopes granted: orchestration:read/operate (McpOAuth.ts:60). External clients get capabilities orchestration, worktree, pull-requests only (McpOAuth.ts:~600) — **no preview/device/html tools**.
3. **`t3 thread` CLI**: mints a short-lived `full-access` MCP client session directly via EnvironmentAuth (no OAuth), revokes at exit (cli/thread.ts:218-229). Requires running server (reads server-runtime.json) and being the same OS user.
- Headers: `Authorization: Bearer`, optional `T3-Mode-Limit: <runtimeMode>/<interactionMode>` to narrow (McpHttpServer.ts:~140-160). Managed policy `maxRuntimeMode` caps clients.
- **Could Fjord (or a Fjord-run model) use it? Yes.** Options: (a) shell out to `t3 thread …` (zero auth work, local only); (b) register as an OAuth MCP client / `claude mcp add --transport http t3 …/mcp` (documented); (c) INFERRED: `t3 auth session issue` (cli/auth.ts:169-200, "scoped bearer access token for headless or remote clients") gives a long-lived token for direct WS/HTTP use — check its `--scope`/`--ttl` flags with `t3 auth session issue --help`.
- Caveat: "A tool that changes another thread needs the calling thread's live run" for thread callers (doc :543); outside clients have no thread so use client-access rules (McpToolAccess.ts: read-only clients get `capability_denied` on writes, :95-100).

## 3. Scheduled tasks / scheduling / queue / delegation
- **Scheduler** (apps/server/src/scheduling/Scheduler.ts): 5-second tick over registered "due work" sources.
- **Scheduled tasks** (scheduledTasks/ScheduledTaskService.ts, 2.4k lines; contracts/src/scheduledTask.ts): a task = title, prompt, project, optional bound thread, workspaceStrategy, modelSelection, runtimeMode, interactionMode, schedule. Schedule types: `interval` (everyMs ≥ 60000), `fixed_time` (timeOfDay HH:MM, weekdays, server local TZ; 10-min missed grace, Schedule.ts:73), `once` (runAt ISO+offset), `webhook`. Bound tasks post into one thread; unbound launch a fresh thread each run. Managed via MCP (`schedule_task` etc.), WS (`scheduledTasks.upsert/setEnabled/delete/runNow/rotateWebhookToken/subscribe/listWebhookDeliveries`, rpc.ts:541-550), and UI. No CLI subcommand for it.
- **Webhook schedule** (this is the closest thing to "inbound events -> agent session"): `POST|PUT|PATCH|GET /api/hooks/:hookId/:token` (environmentHttp.ts:820-838). Optional HMAC-SHA256 signature over raw body (header, hex|base64, prefix; webhookVerification.ts), `filters` (≤16; ops equals/notEquals/startsWith/in/exists on `body.*|headers.*|query.*`, webhookFilter.ts), `dedupe` (replayKey, coalesceKey, window 10–3600s), `maxDeliveryAgeMinutes`, prompt templating `{{body.path}} {{headers.x}} {{query.x}} {{body}} {{request}}`; 1 MiB body cap (webhookRoute.ts:19); delivery outcomes accepted|dispatch_failed|duplicate|coalesced|rejected_signature|disabled|rate_limited|expired|filtered. Public URL (`webhook.url`) only exists with **T3 Connect** (relay `/v1/hooks/:endpointKey/:hookId/:token` forwards to the env tunnel; relay can hold requests ≤24h while offline if opted in; docs/internals/t3-connect.md:7-30). Without Connect, `path` works on local server only. Managed policy can disable webhooks. Prompt says webhook values are untrusted.
  - **INFERRED for Fjord**: GitHub webhooks could target this, but local-only without Connect; for a macOS app polling or its own receiver is simpler.
- **Queue**: per-thread message queue (`t3_queue` list/read/edit/cancel/reorder/promote_to_steer). **Delegation**: `delegate_task` child threads with lineage `subagent`, results flow back to parent (doc :484-533). **Workflows**: only Claude-native workflows (`t3_workflow_stop`, `orchestration.getWorkflowScript/stopWorkflow`); T3 has no user-defined workflow engine.
- Thread states "settle"/"snooze": auto-settle after N days / on PR merge (settings `sidebarAutoSettleAfterDays`, `sidebarAutoSettleOnMerge`), snooze with wake on pending request/failure (doc :419-423). Useful signals for a briefing app.

## 4. Source control & PRs
- Providers: GitHub, GitLab, Forgejo/Gitea, Bitbucket, Azure DevOps, GitCafe (docs/user/source-control.md; packages/source-control-*). GitHub: direct API with token (saved in settings secret store, or GH_TOKEN, or `gh` CLI ≥2.81).
- Server PR model (packages/contracts/src/pullRequest.ts; apps/server/src/pullRequest/PullRequestService.ts, 3.7k lines): list (state, involvement all|reviewing|authored, filters draft/reviewDecision/checks, per-project, query; entries have checksState passing|failing|pending, reviewDecision, mergeability, viewerReviewRequested, labels, stack), detail (checks[{name,status pending|action-required|success|failure|skipped|neutral|cancelled,required}], reviewers, body, headSha, behindBy, autoMerge…), activity/comments (issue-comment|review-comment|review), threads, diff, review guides, actions (merge, update, comment, submit review, reply, resolve, reactions, reviewers, labels). All over WS (`pullRequests.*`, rpc.ts:552-588) — **PRs only, not issues**; scope is PRs of registered *projects* (error "No project … is a checkout of <repo>" for others, pullRequests/tools.ts:~215).
- Thread<->PR linking: `link_pull_request(s)` / `t3_thread_update link_pull_request`, plus `branchPullRequest` from branch; thread shells carry `linkedPullRequest`, `pullRequests[]` with last state (OrchestrationV2ThreadShell, orchestrationV2.ts:2083-2085); `pullRequests.linkedThreads` RPC; prompt links `https://app.t3.codes/new?pr=owner/name/123&prompt=…` open the linked thread or a new worktree on the PR branch (docs/user/prompt-links.md). Auto-settle on merge.
- **PR watch** (orchestration-v2/PullRequestWatchReactor.ts, pullRequestWatch.ts): agent calls `watch_pull_request` (open PRs only; subagents can't). Server **polls the host every 2 minutes** (`SWEEP_MINUTES = 2`, :43) with fingerprint checks and full rereads (10/30 min fallbacks), concurrency 4, and *wakes the thread's agent* (a message into the thread) on: checks-failed (failed/cancelled/action-required), checks-passed (required checks, or all if none required), new remarks (comments/reviews from others, edits included), no-checks after 15 min, conflicting. Comment-only wakes capped at 10 in a row. Watch ends on Stop/merge/close.
- **Can T3 host Fjord's Triage rules or feed them?** INFERRED: T3 can *feed* them partially — `pullRequests.list` over WS returns cross-project PR lists with checksState/reviewDecision/mergeability (the same data triage rules need) for registered projects' repos, using the user's already-configured credentials, and `pullRequests.subscribeRefreshes` exists (not read). T3 has no rule engine, no issue support, no CI beyond PR checks, and PR watch only wakes agents, not external listeners. Handing an item to an agent = `t3_thread_launch` with `pr` context via prompt link or `delegate_task`; or CLI `t3 thread start <proj> "<prompt>" --worktree <base>`.

## 5. Extensibility & misc
- **No plugin/mod/extension system** for server or web UI found (no plugin loader in apps/server/src; extensibility is via providers, MCP, themes, settings, scripts). Adding a provider = code (docs/internals/adding-a-provider.md); ACP Registry drivers can be added at runtime (`server.setAcpRegistryProvider`). Pi gets a T3-owned extension file injected (doc :158-170).
- **MCP Apps** (apps/server/src/mcpApps/, contracts/src/mcpApps.ts): *consumes* MCP Apps UIs returned by third-party MCP servers; rendered in-thread, can call tools on own server and post messages (user prompted). RPC: mcpApps.callTool/toolInfo/readResource/updateModelContext. It is not a way to extend T3 with your own UI, and T3's own MCP server does not return apps (INFERRED).
- **HTML renders** (docs/user/html-renders.md; `html_preview` tool): agents publish sandboxed HTML pages shown in the thread, themed; headless Chrome ~120MB managed by T3.
- **Themes**: custom themes in UI (import T3/VS Code JSON); environment themes in `~/.t3/userdata/themes` published by `t3 theme set`; `defaultTheme` setting. **Keybindings**: `~/.t3/userdata/keybindings.json` (server.upsertKeybinding RPC); client-side shortcuts.
- **Settings**: `~/.t3/userdata/settings.json`, schema `ServerSettings` (contracts/src/settings.ts:1186+): favorites, providerModelPreferences, worktreeCleanup, storageCleanup, worktreesDirectory, responseStreamingMode, enableProviderUpdateChecks, continueThreadsAfterServerUpdate, enableAgentBrowserAccess(+project overrides), defaultAutoPull, defaultProjectScripts/projectScriptOverrides, defaultModelSelection, fallbackModelSelection, defaultRuntimeMode, projectSettingsOverrides, enableAgentDeviceAccess/enableDeviceSupport/deviceHosts/easDeviceHosts/simlockDeviceHosts, sidebarAutoSettle*, idleCompaction, snoozeLimitedThreads, autoResumeLimitedThreads, snoozePresets, hiddenThreadTags, guestSharingEnabled, linkedEnvironmentsEnabled, backgroundActivity(+profile, automaticGitFetchInterval, providerHealthRefreshInterval), defaultTheme, environmentIcon, defaultThreadEnvMode, newWorktreesStartFromOrigin, worktreeSubmodules, addProjectBaseDirectory, textGenerationModelSelection, threadTitleInstructions, branchNamingMode/Prefix/Instructions, removeAgentCreditsOnMerge, sourceControlWritingStyle/WriterModelSelection, reviewGuidesEnabled/ModelSelection/Instructions, pullRequestMergeMethod, providerInstances, observability, sourceControlHosts, usageLimitSources, secretProviders (1Password package), cursorKeychainUsageEnabled, usagePriceOverrides, usageModelAliases, usageModelFilter, plus provider settings (Codex/Claude/Antigravity). Env/server settings change via RPC `server.updateSettings`.
- **Managed policy** (docs/user/managed-policy.md; apps/server/src/policy): admin JSON (`schemaVersion`, `organization`, `settings{path:{value,locked}}`, `limits{maxRuntimeMode, clients, telemetry, providers…}`) at macOS `/Library/Application Support/T3Code/policy.json` or configuration profile `com.t3tools.t3code`; read at server start; refuses to start on invalid. `t3 policy show|check|templates`. Currently installed one is visible in server-runtime.json key `managedPolicy`.
- **Prompt links**: `https://app.t3.codes/new?prompt=&repo=&provider=&model=&pr=` opens a draft, never auto-runs; thread links `…/threads/<env>/<thread>`. Hidden characters stripped.
- **Guest links** (beta, Settings→Labs): read-only follow + questions from a browser; guest messages wait for owner send (`pendingGuestMessageCount` on shell). `guestShare.create` RPC.
- **Devices**: iOS Simulator/Android emulator panel; agents control via `device_*` MCP tools.
- **Secrets**: server secret store (`~/.t3/userdata/secrets`, not read), `request_secret` MCP tool, pluggable secret providers (1Password).
- **Environments / remote**: T3 Connect (Clerk + Cloudflare relay, managed tunnel, ≤3 machines/account), Tailscale, LAN, pairing tokens/sessions; linked environments let agents act on other machines (`t3 environment link`, Settings→Labs flag `linkedEnvironmentsEnabled`).
- **Notifications**: mobile push via T3 Connect relay (AgentAwarenessRelay.ts publishes agent activity: finished/failed/needs approval/input; docs/user/mobile-notifications.md); desktop/web notifications client-side (apps/web/src/threadNotifications.ts, ThreadNotificationCoordinator.tsx; desktop badge ipc). Not exposed to external programs.
- **Activity log**: UI-only summarisation of tool calls (docs/user/activity-log.md). **Usage tracking**: `server.getUsageSummary` RPC; reads provider transcripts/APIs (apps/server/src/usage); docs/user/usage.md. Observability: trace file (`t3 trace summary`), OTLP (settings.observability).
- **T3 "triage"** = a support flow: `t3 triage` or palette "Triage an issue" launches an agent with logs/state + a clone of T3's source at this version to help file a GitHub issue (docs/user/triage.md; apps/server/src/triage/TriageService.ts). Not PR/issue triage; no relation to Fjord Triage.

## 6. Hooks / lifecycle callbacks to external programs

  4. Provider-native hooks (Claude/Codex hook configs) are the agents' own and unaffected; INFERRED that Fjord's existing hook-based channel for Claude/Codex would still work inside T3-launched sessions as T3 wraps the provider SDKs, unverified.
  5. Scheduled-task webhooks are *inbound* only.

## 7. Fork-friendliness
- License: **MIT** (LICENSE: "Copyright (c) 2026 T3 Tools Inc."). third-party-licenses/ included.
- Monorepo (pnpm workspace, ~31.5k tracked files). Non-test TS/TSX lines: apps/server ≈240k, apps/web ≈291k, apps/desktop ≈42k, apps/mobile ≈148k, packages ≈292k (30 packages incl. contracts, shared, client-runtime, provider-* x10, source-control-* x9, effect-acp, effect-codex-app-server, ssh, tailscale, secret-provider-*). Plus infra/ (relay Worker), native/, oxlint-plugin-t3code, evals/. Effect (beta v4-style `effect/...` imports) throughout. So a full fork is very large (~1M lines); patching is high-maintenance.
- CONTRIBUTING.md: "not actively seeking outside contributions"; features need prior maintainer approval; bug fixes/perf/reliability welcome. AGENTS.md: priorities (open core, performance, remote-ready, multi-surface web/desktop/mobile), "A large number of our users run forks", minimal/yagni philosophy; many internals docs under docs/internals.
- **INFERRED recommendation**: do not fork; treat T3 as a platform. A native macOS app can talk to the installed server via (a) `t3` CLI, (b) `/mcp`, (c) the WS RPC (contracts are typed Effect schemas in packages/contracts, MIT, could be ported to Swift codable by hand). Rapid version churn (v0.1.x, contracts change) implies pinning to server version; `/.well-known/t3/environment` descriptor and `server.probe` give version info.
