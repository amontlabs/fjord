# F2 Part C: Remote computers (Silo / SSH guests), Claude dependencies

Paths relative to `/Users/polarzero/code/projects/lookout`. Sources = `Sources/Fjord/`. Docs = `docs/design/silo-api/`. "INFERRED" is marked. No git, no app run.

## 0. Big picture (what exists)

Fjord does NOT run or control Claude on a guest. The guest runs **Claude Desktop's own SSH session** (Desktop on the Mac spawns the Claude Code engine on the guest over SSH; docs 70-fjord-needs.md:33-37, 1.1). Fjord only:
1. Writes a Claude Desktop SSH connection (`sshConfigs` in the Mac's `~/.claude/settings.json`) pointing at an SSH alias Silo creates (ClaudeSSHSettings.swift:94-163; SiloGuestClient.swift:151-156).
2. Installs, in the guest, a Claude Code plugin (its hooks module `register.ts`), a PermissionRequest command hook (Node script) in the guest's `~/.claude/settings.json`, a Node runtime if missing, a relay key, and inbox/presence/forms folders (GuestRouterInstaller.swift:38-103).
3. Watches guest files (presence, registry, forms, transcripts, background-task outputs) through Silo `guest.files.*` / `guest.exec` and mirrors them into the same stores that drive local Claude sessions (GuestRouterRuntime.swift:464-541).
4. Delivers messages/answers by writing files into the guest (signed `.msg` into inbox, `<id>.answer.json` into forms) that the guest plugin/hook consume (GuestRelayInbox.swift:56-114; GuestForms.swift:71-87).
5. The **session itself must be started by the owner in Claude Desktop** (`claude://code/new?ssh_host=...` link, one Send click). Fjord only matches the Desktop session to the guest afterwards (GuestDesktopStart.swift:41-77; docs triage-in-computers-options.md:11, 70 §1.3).

**Observation (code state):** in `Sources/Fjord`, nothing appends to `runsOnProjects` or `pendingDesktopStarts`, and nothing calls `GuestRouterInstaller.install` or `ClaudeSSHSettings.install` or opens `claude://code/new` / `ssh_host` (greps of all Sources: only decode/persist at Router.swift:23-25,83-86; installer `install` only called from Tests/FjordTests/GuestRouterTests.swift:154,189,208; `ClaudeSSHSettings.remove` only from GuestRouterRuntime.swift:151,250). `GuestRouterInstaller.disable` and `ClaudeSSHSettings.remove` ARE reachable (RouterView.swift:43 `disableAll`, Store.swift:33). So the "Runs on a computer" producer (picker, install, link open) is absent from this tree at this commit; the consumer side (watch, deliver, answer, cancel, status) is wired (RouterMCP.swift:957-982, RouterRun.swift:452-470, RouterCancel.swift:27-52, RouterView.swift:87-137, RouterDispatcher.swift:807-819,1090). INFERRED: the start flow was removed or not yet re-wired; docs still describe `GuestDesktopStart.swift:47-54` as the link opener (triage-in-computers-options.md:11), which no longer exists in that file.

## 1. Entries

### 1.1 Claude Desktop SSH connection (`sshConfigs`)
1. User sees: nothing directly; a computer becomes pickable in Claude Desktop's Code tab "SSH" host list as "`<computer name> · <owner>`". Owner confirms the connection the first time in Desktop (docs triage:11, 70:178 "Desktop asks to confirm the connection first").
2. Mechanism: Fjord edits Mac `~/.claude/settings.json` key `sshConfigs` = array of `{id, name, sshHost}` (ClaudeSSHSettings.swift:106; install :125-136; remove :138-148). id = `fjord-<deviceId|local>-<computerId>`, `fjord-dev-` prefix for debug builds (:110-112). `sshHost` = alias returned by Silo `guest.sshAlias.ensure` (SiloGuestClient.swift:151-156; GuestClient.swift:152-153); that alias is an `~/.ssh/config` entry using ProxyCommand (docs 70:155-178). Desktop connects with system OpenSSH (docs 70:43-47).
3. Direction: Fjord -> file (Mac). Read-compute-reread-atomic-replace, 3 attempts, serialized by lock, first original backed up to `settings.json.fjord-backup` (ClaudeSSHSettings.swift:22-63; backup path :116). Idempotent (no write if entry equal, :130).
4. Failures: invalid JSON / non-object / unreadable / kept changing -> Fjord leaves file alone with message (ClaudeSSHSettings.swift:12-18); incompatible `sshConfigs` shape -> refuse (:154-163, :171-172). Symlinks resolved and rechecked (:32,67-82).
5. Constraints: Desktop matches saved connections by user, host, port (docs 70:178). Plugin hooks are NOT copied by Desktop to SSH hosts, so hooks must live in the guest's own plugin/settings (docs 70 §1.1 "Plugin hooks are not copied", :84-ish; GuestClient comment GuestRouterInstaller.swift:5-6 "never calls Fjord or a controller path"). Owner decision: Router "Runs on" = Claude desktop app sessions over SSH, "Fjord writes the SSH connection" (70:35).
6. Removal: when a computer is deleted, Fjord removes the `sshConfigs` entry + Silo alias, persisted as `pendingGuestRemovals` and retried on `connections.devices.changed` events / reconnect (GuestRouterRuntime.swift:139-160, 247-253, 255-297; Store.swift:33-37; ComputersModel.swift:625-648 hook).

1. User sees: AskUserQuestion questions and ExitPlanMode plans from a remote session appear in Fjord's Router/brief like local ones, answerable there (RouterView.swift:81-137 `guestPendingForm`, answer routing at :109, :135).
2. It writes `forms/<session>-<ms>-<pid>.json` {key, session_id, transcript_path, cwd, tool_name, tool_input, created_at, pid} (0600, fsync) (:376-388), polls every 250 ms up to 24 h for `<key>.answer.json`, and rewrites the form with `tool_use_id` found by scanning the transcript tail (8 MiB) for the matching `tool_use` (:343-357, 392-406). ### 1.6 Relay inbox: delivering the owner's words to a guest session
1. User sees: a message sent from Router to a computer session arrives in that Desktop SSH session as the owner's own words; Fjord shows delivered / refused / unconfirmed with retry (GuestRelayRecord states, GuestRelayInbox.swift:3-31; retry GuestRouterRuntime.swift:372-390; RouterDispatcher.swift:807-819).
2. Mechanism: Fjord signs a v1/v2 relay message with the guest's `relay.key` (read via guest.files; must be 64 hex chars) using `RelaySigner.sign(body, target, key, nonce, now)` where `now` is the GUEST clock (sampled via Node `Date.now()` with monotonic midpoint, GuestClock.swift:5-22; GuestRelayInbox.swift:226-237; RouterMCP.swift:963-974). Writes `~/.local/share/fjord/router/relay/<cliSessionId>/<nonce>.msg` (0600, create-only) and waits for `<nonce>.ack` ("ok" / "ok ..." / "refused: <why>") via `guest.files.watch` hints + rereads, 6 s default (`RelayInbox.wait`, ClaudePlugin.swift:1410) (GuestRelayInbox.swift:56-114, 138-157, 159-190). The guest plugin (`register.ts`) polls the folder every 0.5 s, verifies MAC/target/freshness/nonce, then `$.prompt.submit({ text: body, asUser: true })` (ClaudePlugin.swift:192-215 comment, :535). Then Fjord deletes both files (GuestRelayInbox.swift:176-190).
3. Pre-send requirements: guest presence for that CLI session must list capability `inbox-v1` (`ClaudePlugin.inboxCapability`, ClaudePlugin.swift:147) else `notRunning` / "has no live guest inbox presence; nothing was sent" (GuestRelayInbox.swift:233-235; RouterMCP.swift:975-978). Fjord also checks `Router` is on, gate/preflight closures (GuestRelayInbox.swift:75-95).
4. Idempotency: the signed payload is persisted (`guestRelayDeliveries` ledger, limit 500, GuestRelayInbox.swift:240-255; Router.swift:27) BEFORE the first write; same nonce reused on retry; an existing message with different content -> `duplicateNonce` (GuestRelayInbox.swift:192-199); timeout leaves state `unconfirmed` and never resends with a new nonce (:100-107, errors :36-48). Stale files older than `RelayInbox.leftover` (15 min, ClaudePlugin.swift:1412) swept (GuestRelayInbox.swift:116-127).
5. Abort: `abort-v1` capability; Fjord writes a signed abort control file into the same inbox (`RelaySigner.signAbort`) after confirming presence lists `abort-v1`; guest ack reveals how far the delivery got (RouterCancel.swift:27-52; GuestRouterRuntime.swift:404-412; RouterDispatcher.swift:1090-1091).
6. Constraints: no peer-channel fallback for guest sessions (docs 70 §2 row i: "For guest sessions, the inbox (row a) is the only path"; cross-machine SendMessage needs Remote Control). Session must be live: Desktop stops warm idle processes, so a quiet session may need its page opened first (triage doc :105 "D is part of every design"; the code here does not open the page - no `claude://` open in Guest*).

## 2. Starting / waking / stopping a session on a guest (explicit answers)

- **Start:** Fjord CANNOT start a Claude session on a guest by itself. Mechanism per docs: owner clicks Send on `claude://code/new?ssh_host=<alias>&ssh_folder=<path>&q=<task>` in Claude Desktop (70:178; triage:11 "1 click per session (plus the connection confirm the first time)"). Desktop (on the Mac) spawns the Claude Code engine on the guest over SSH. Fjord then matches it (1.8). `claude://code/new` "never sends it for you" (70 §1.1). Not found in Sources at this commit (see section 0).
- **Ruled-out autostart routes (docs, Desktop 2.31226.1 / 2.37337.1, static analysis):** `claude://resume` is local-only (triage:63; 70:~76); forged `local_*.json` records only load at Desktop init, no external reload trigger (desktop-session-reload.md Summary); mod/plugin `$.mcp.call("ccd_session","start_session")` is refused unless the open turn was started by a person at Desktop's composer (desktop-mod-session-start.md §2.2, summary table M1/F); mobile/Remote Control inbound bridge only starts Cowork sessions (desktop-ssh-new-session-final-fable.md §1.1-1.2); `claude remote-control` server, `--desktop`, `--teleport`, `--cloud`, `--attach-serve` ruled out (final-fable §0.1, §4, §6).
