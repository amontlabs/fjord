## 0. Architecture in one picture (SF/CourierCore.swift:3-6, EV:5-10, BJS:1-5)

```
claude.ai/code tab (Chrome, pinned, "#fjord") --content.js (MutationObserver, DOM only)--> chrome.runtime Port
 --> extension service worker (background.js) --> chrome.runtime.connectNative("dev.fjord.router")
 --> `Fjord --native-host` (stdin/stdout, 4-byte native-endian length-prefixed JSON)
 --> Unix socket `<AppSupport>/Fjord[ Dev]/router.sock` (JSON lines) --> CourierHost (actor) --> CourierCore (engine) --> router.db (SQLite)
```
- The Swift engine is a "line-for-line port" of the Python `poc/router/routerd.py` (SF/CourierCore.swift:3, CourierHost.swift:5). `poc/router/*.py` and the Python tests are the conformance reference; Swift test bridge `Fjord --courier-test --db <path>` (SF/CourierTestMode.swift:3, main.swift:7-8).
- Docs say the whole claude.ai private-route knowledge is "Not for shipping" (conflicts with Anthropic Consumer Terms / Claude Code credential rules unless Anthropic gives permission) (INT:6-7). INT:140 item 7 "Anthropic's terms on automating claude.ai" is still listed under "Still to test".
- KEY FACT: the shipped path never calls claude.ai HTTP APIs itself. It drives the real web UI by DOM (typing in the real composer, clicking real buttons), and only OBSERVES the page's own network calls through `PerformanceObserver` resource timing (CJS:867-905). The private-route table (INT:23-45) is research from the POC (`poc/projects/ProjectsPOC.swift` WKWebView `fetch`; INT:116-122), not used by `Sources/Fjord` (grep of `Sources/Fjord` for `/v1/code` finds no request code; INFERRED from absence plus CJS comments; `RouterBriefs.swift:582` only builds a browser URL).

### 1.1 Sending your words to a claude.ai project's coordinator or to a thread ("Delivered to X")
1. User sees: a pill over the composer "Sending to <project · thread>" -> "Delivered to ..." ; or "Not delivered" with the engine's plain-sentence cause; or "Waiting to send" with one button (Open Chrome / Sign in / Open Fjord's tab / Check the setup / Show the Claude app) (SF/RouterCourier.swift:524-540, 69-82, 288-300).
2. Mechanism: `RouterCourierPills.send` -> `CourierRequest.send(words,project,thread,key)` (RouterCourier.swift:369-372, CourierHost.swift:13) -> `CourierHost.submit` (CourierHost.swift:501-535) -> `CourierCore.say` (CourierCore.swift:1386-1393; "the engine never calls a model", target must be explicit) -> `explicit` builds intent tool `send_to_project` (project chat, the coordinator) or `reply_in_thread` (thread composer) with proof `{"kind":"latest_you",project,thread,words}` (CourierCore.swift:1367-1382). `CourierCore.sends` = those two (CourierCore.swift:194). Run state machine per EV:160-293: `open` command (page: `history.pushState` to `/code/project/<chan_id>[?thread=<cmsg_key>]` + synthetic `popstate`, no document load; CJS:693-764) -> `send` command typed into real composer, then clicked.
   - Page command `send` (CJS:766-837): finds composer `[data-testid="code-prompt-input"]` (first = project, second = thread; CJS:35,44-48), send button `[data-testid="code-prompt-send"]` nearest ancestor (CJS:67-74). State machine: draft has other words -> `document.execCommand("selectAll")`+`"delete"`; draft empty and Send enabled -> wait (page finishing last send); draft empty and Send disabled/missing -> `execCommand("insertText", false, text)` once; words in draft and Send enabled -> `button.click()` once. Never types if a settings dialog is open or focus can't be taken (CJS:803, error "a dialog is open", CourierCore.swift:178,1280).
   - Proof of delivery is a later DOM-read `rows` event (EV:265-295): a new row from you after a baseline of the latest 50 on-screen keys + 200 known keys (CourierDo.swift:14-15,132-141), words compared loosely (markdown rendering), one row proves one send. Row identity = `data-entry-key` (`cmsg_...`, `cmsg_pending_...`, `provisional:...`) (CJS:268-270); author from `data-perf-row` (`assistant`/`human`/`marker`) (CJS:331); streaming from `data-perf-row-streaming` (CJS:333).
3. Direction/payload: out = `{id,kind:"send",side,text,project,thread,intent,click_only}` (EV:164); in = `rows`, `composer`, `done` events. Latency: attempt deadline 20 s (`CourierDo.timeout`, CourierDo.swift:13), `TAKE_WAIT` 2 s (CourierCore.swift:188), accepted/queued wait 300 s (`acceptedWait`, :180), `retries = 2` (CourierDo.swift:12). Idempotency: app-side `key` (a repeat of the same key while the intent hasn't failed returns that intent; CourierHost.swift:512-520); 120 s duplicate window (`dupWindow`, CourierStore.swift:7, CourierHost.swift:498); never re-type once a click was reported or the page "took" the words (empty draft after click) (EV:178-234); `click_only` retries (CJS:810).
4. Failure modes handled: `refusal` ("this folder has no Claude project yet", "that thread isn't on the board", "no such project on the page"; CourierDo.swift:79-85); composer replaced by a note (archived project; `[data-composer-stand-in]`, CJS:53-64) -> refused; page reload right after click ("the tab reloaded right after the click..." 5. Constraints recorded: reply goes into the thread's composer on the claude.ai page, i.e. a message sent by the web UI as the user (INT:104-109 says the web UI path frames it as human; raw API `/sessions/:id/events` would be framed peer and "forging" the client headers is explicitly refused INT:112-114). Project sends reach the coordinator (a cloud session) which "picks the thread or starts one" (RouterProjectDecide.swift:185). Words sent as-is plus possible Fjord notes (RouterDispatcher.swift:642 `RouterPointers.attach`; other slice).

5. Constraints: INT:130-139 (a killed local thread: channel reply not delivered and does not restart it; coordinator's claim of restarting can't be trusted; `SendMessage` to `local_<id>` cold-starts the process but loses the project link). ### 1.3 Answering a thread's decision card (question/plan) from Fjord
1. User sees: pill "Answering in <project · thread>" -> "Answered: <option text>" (RouterCourier.swift:374-379, 543-560).
2. Mechanism: `CourierRequest.answer(project,thread,card,option)` -> `CourierCore.answer` (CourierCoreFramesAnswer.swift:13-28), intent tool `answer`, words `"<card>#<option>"`. Runs in a hidden thread frame (see 1.5), not the top tab. Command to page `{"kind":"answer","id","project","thread","card","option"(1-based),"frame"}` (CourierCoreFramesAnswer.swift:49, EV:563). Page `answerStep` (CJS:1550-1567): in the thread frame, once its settled read is in (`told.owed.thread` false), finds the row whose descendant `data-entry-key == card`, `[data-testid="decision-card"]` w/o `data-state` (pending), clicks the Nth `ul[role="list"] button`. Refuses: "already answered" (card has `data-state`), "card gone", "no such option", "not this thread's frame"; never clicks a button with `aria-busy`/`aria-disabled`/`disabled`.
   - Option text read as "label — consequence" via `aria-labelledby`/`aria-describedby` (CJS:294-304).
3. Proof: card `answered` (card gets `data-state`) in the frame's rows, then the thread's row status `working` (CourierCoreFramesAnswer.swift:70-76). Attempts 2 (`answerAttempts`), deadline 20 s each (:10,51,78-91). A confirmed answer is recorded in the log as `answer:<intent id>` item for briefs (:114-119).
4. Failures: "the answer was not confirmed: the card never showed answered" (+frame notice), "the card shows answered, but the thread never showed working", "the frame went before the answer was confirmed"; restart: "routerd restarted before the answer was proved" - a click is never sent twice across a restart (CourierCore.swift:333-334).
5. Constraint: "Fjord clicks nothing in a prompt" for permission/approval slots; approval is only READ (`dockState`: `rail-composer-dock`, `code-prompt-stop`, `[data-approval-cluster-host]`, `[data-approval-dock]`; CJS:619-629). So approving a tool-permission prompt in a claude.ai cloud thread is NOT done by Fjord; answering a decision card is.

### 1.7 The "open Claude" desktop handoff avoided
claude.ai's project-link handoff sets `window.location.href = "claude://claude.ai/code/project/..."` when Chrome freshly loads a project link while the desktop app is installed, visible, and the preference `code-project-links-keep-in-browser` is unset (INT:227-235). Fjord avoids it by never loading a project link: `open` uses `history.pushState` (no document load; EV:235-237, CJS:680-684), restored tabs load the projects page (BJS:378). Frames are iframes loaded with `/code/project/<id>` src (CJS:1461): the doc does not say if the handoff applies to them (INFERRED: the frame's `window.top !== window` so the page's `window.location.href` assignment may apply to the frame; not stated).

## 6. Constraints / risks the repo itself records
- "Not for shipping" (INT:6) because automating claude.ai conflicts with Anthropic terms.
- Selectors are by test id and structure, "never by visible text" because UI is French (CJS:1; user's macOS is French); labels follow the language (INT:167). Many selectors depend on claude.ai internals (`data-home-*`, `data-perf-row`, `data-epitaxy-entry-index`, `transcript-sizer`, `code-prompt-*`, `settings-top-row`, `project-preapproved-folder*`, `overview-thread-row`, `decision-card`, `channel-created-thread-glyph`); any claude.ai redesign breaks them. Missing elements give "unknown", never a guess (EV:689).
- Hidden-tab behavior drives much complexity: timers throttled (15-20 s late), no animation frames so closed dialogs keep `data-closed`, popup presses ignored until ~1.5 s (CJS:1183-1191, EV:333-354); `wake_me`/`wake` messages replace timers (CJS:1583-1604).
- Chrome only, Mac only; one tab, one composer, runs serialized (`advanceAll`; CourierCoreRuns.swift:34-39).
- A reload ~0.1 s after a click can lose the message (EV:633-636); server may queue the message behind a coordinator turn (INT:169).
- Frame loads grow the renderer: handover to a fresh tab at budget 6 (BJS:94-99).
- Missing sign-in is only detectable when the tab is on a claude.ai page; Chrome profile picker/other profile means extension absent (CourierDo.swift:28).
- No cloud/Web threads other than via project coordinator; "cloud threads and marks in other projects" had no cheap live signal before the frames design (INT:173-179).
